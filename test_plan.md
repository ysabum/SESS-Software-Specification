# SESS Test Plan

## 1. Test Basis and Conventions

This plan tests the seven acceptance criteria in `spec.md` and adds extra cases for requirements or test dimensions not adequately covered by those criteria. It does not assume an implementation technology or invent response schemas.


### Expected Status and Body Conventions

- `spec-defined success`: the requested behavior succeeds. The specification does not define an HTTP status code.
- `spec-defined rejection`: the request is denied or rejected as stated in the specification. The exact status code and error-body schema are unspecified.
- `body fields`: describes the information that must be observable; exact JSON property names are not specified.
- `side effects`: records, sessions, summaries, audit events, or other state changes required or prohibited by the specification.
- For every rejection, verify that the rejected operation created no protected or business object and did not disclose patient or source information. Where the specification requires an audit event for the rejection, that audit event is the permitted side effect.


## Test Data Assumptions

Use controlled test accounts, patients, records, timestamps, configured roles, a configured session timeout `T`, and a representative workload. The deploying organization must supply its role policy, timezone, operating hours, representative dataset, and workload. These values are not fixed in the specification.

## 4. Spec Gaps

The following are traceability gaps between the requirements and acceptance criteria. They are listed for clarification and are not resolved by this test plan.


### 4.1 Requirements With No Acceptance Criterion, or Only Partial Coverage

| Requirement | Gap |
|---|---|
| **NFR-001: Security and Privacy** | AC-001 covers login, patient authorization, and inactivity, but does not verify PHI protection during transmission/storage, alteration/destruction protection, configurable role and patient-access policies, or the security of all SESS functions. |
| **NFR-002: Accuracy and Clinical Reliability** | AC-002 does not explicitly test preservation of source meaning or identification of conflicting and incomplete source information. |
| **NFR-003: Traceability and Verifiability** | AC-004 and AC-006 cover source access and context, but do not explicitly require a source link for every clinical item or a section/data-element reference when available. |
| **NFR-004: Performance** | No acceptance criterion tests the 3-second search target, 10-second summary target, 95% success proportions, representative dataset/workload, or measurement start/end points. |
| **NFR-005: Usability and Workflow Efficiency** | No acceptance criterion tests whether a basically trained healthcare professional can complete the specified workflow without technical assistance, or whether summary/source content, detail level, and categories are understandable. |
| **NFR-006: Availability and Fault Handling** | AC-002 partially covers partial retrieval and stale information, but does not test the 99.5% monthly availability target, scheduled-maintenance exclusion and advance communication, complete EHR/network outage behavior, historical-summary labeling, or all stale-data rules. |
| **NFR-007: Interoperability and Data Compatibility** | No acceptance criterion explicitly tests the agreed/documented EHR interface, preservation of source meaning/identifiers/timestamps/context, reporting uninterpretable or unimportable records/fields, configured-timezone display, or single-retrieval consistency and regeneration after concurrent changes. |
| **NFR-008: Auditability** | AC-007 tests summary-generation audit fields only. It does not cover authentication events, patient-record access, permission changes, failed authorization, source viewing, audit-record access, authorized audit access, or audit-record immutability. |

**FR coverage:** FR-001 through FR-006 each have at least one named acceptance criterion: AC-001 through AC-006 respectively.


### 4.2 Acceptance Criteria Without a Corresponding Requirement

None identified. AC-001 through AC-006 map to FR-001 through FR-006, and AC-007 maps to NFR-008.


### 4.3 Underspecified Behavior That Prevents Exact Expected Values

1. **HTTP/status and response schemas:** The specification does not define HTTP status codes, JSON field names, error codes, or exact error-message text.
2. **Authorization policy:** Exact roles, permission matrices, patient-assignment rules, and access-revocation propagation are not defined.
3. **Session timeout:** The timeout is configurable, but no default value or exact-equality behavior at the timeout boundary is specified.
4. **Summary levels:** Brief, Standard, and Detailed are named, but their precise content/completeness rules are not defined.
5. **Search behavior:** Empty queries, invalid filters, result ordering, pagination, no-match behavior, and combinations of filters are not specified.
6. **EHR behavior:** No EHR vendor, version, API, test environment, or detailed failure contract is specified.
7. **Freshness and retention:** No freshness threshold, summary retention duration, cache policy, or version-history behavior is defined.
8. **Concurrency:** The required outcome when a consistent summary cannot be produced is stated, but detection and conflict-resolution behavior are not.
9. **Availability measurement:** Operating hours are organization-defined; the specification does not define rounding, incident accounting, or how partial outages affect the 99.5% calculation.
10. **Audit behavior:** Retention duration, timestamp precision, ordering, query/listing behavior, and exact authorized roles for audit access are not specified.
11. **Input validation and error precedence:** The specification does not define malformed-input responses or precedence when multiple failure conditions occur at once.
12. **Usability measurement:** “Basic system training” and “without needing technical assistance” are not operationally quantified.



## 5. Review of Expected Values

The expected outcomes above are limited to what the two source documents support:

- The three summary detail values are exactly **Brief, Standard, and Detailed**.
- Search and summary performance targets are **3 seconds** and **10 seconds**, respectively, for **at least 95%** of requests under a representative workload.
- Availability is **at least 99.5% per calendar month**, excluding scheduled maintenance.
- The session rule is based on inactivity **longer than** the configured timeout; exact equality is left open.
- The PHI category list contains **eleven categories**, all listed in AC-005's test cases.
- Every clinical summary item requires a source-record link; a section/data-element link is required **when available**.
- Timestamps must preserve the source value and display in the organization's configured timezone.
- Partial retrieval must show successfully retrieved information and identify unavailable categories.
- Stale information is information shown because current retrieval failed; it must be identified as stale and show its original retrieval timestamp.
- A summary must represent information retrieved during one summary-generation request; if a consistent summary cannot be produced because records change during retrieval, the user must be notified and required to regenerate.
- Audit records must include user, action, applicable patient/record reference, and timestamp, and must cover the event types listed in NFR-008.

No numeric thresholds, HTTP codes, schemas, role names, or error precedence rules have been added where `spec.md` and `architecture.md` do not provide them.
